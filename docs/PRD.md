# PRD: 금융문서 민감정보 점검 웹 서비스

- 프로젝트명: IM-BANK
- 최종 수정일: 2026-11-09
- 상태: draft

## 1. 배경과 문제 정의

iM뱅크 주최 대회의 과제는 "AI기반 금융문서 민감정보 자동 식별 및 위험도 등급화"입니다. 팀은 Upstage Studio에서 문서를 인식·분류·추출·판정하는 워크플로를 만들었고, 제출 기본안 v4.2(정책판본 2026-11-09.5)는 평가 문서 10건을 2회 실행해 두 번 모두 등급과 사람 검토가 정답표와 일치했습니다. 2회차는 Extract 결과를 캐시에서 재사용했고, v4.2의 추출 행 단위 채점은 아직 하지 못했습니다. 이전 버전(v3.4, v2.5)은 기록으로 남깁니다. 자세한 과정은 워크플로 변경 설명과 Studio 버전 안내에 있습니다.

금융기관 실무자는 대출 신청서, 거래내역서, 보험금 청구서 같은 문서를 외부에 제공하거나 다른 부서와 공유하기 전에 주민등록번호, 계좌번호, 건강정보 등이 드러나 있는지 직접 확인합니다. 이 작업에는 다음 문제가 있습니다.

- 문서마다 서식이 달라서 확인에 시간이 오래 걸리고, 사람이 놓치는 항목이 생깁니다.
- "이 문서가 얼마나 위험한가"를 판단하는 기준이 사람마다 다릅니다.
- 판단 근거가 기록으로 남지 않아서 나중에 설명하기 어렵습니다.

Studio 워크플로는 이 판단을 자동화하지만, Studio 화면은 워크플로를 만드는 사람을 위한 도구입니다. 실무자가 문서를 올리고 결과를 확인하며, 검토자가 애매한 문서만 골라 확인하는 **업무용 화면**이 필요합니다. 2026-11-06에 v2.5를 Agents API로 호출할 수 있음을 확인했으므로, 이 API를 호출하는 웹 서비스를 만듭니다.

## 2. 목표와 비목표

### 목표

1. 문서 한 건을 올리면 90초 안에 위험 등급, 사람 검토 여부, 판정 근거를 보여 줍니다.
2. 발견한 민감정보를 **원본 문서 위의 정확한 위치**에 표시하고, 보고서 문장과 문서 위치를 서로 연결합니다.
3. 점검 담당자, 검토자, 관리자 역할을 나누고, 원문 열람과 검토 결정을 감사 기록으로 남깁니다.
4. 대회 시연에서 평가 문서 10건의 웹 실행 결과가 정답표와 모두 일치함을 보여 줍니다.

### 비목표

- **판정 로직을 백엔드에서 다시 구현하지 않습니다.** 위험 등급과 사람 검토 판정은 Studio 워크플로만 내립니다. 백엔드는 결과를 해석해 보여 줍니다.
- 실제 고객 문서를 처리하지 않습니다. 대회가 제공한 합성 문서만 사용합니다.
- 법적 판단이나 유출·위법 여부를 확정하지 않습니다. 결과는 자체 점검 기준에 따른 참고 정보입니다.
- 여러 금융기관을 위한 조직·테넌트 구조를 만들지 않습니다.
- 워크플로 프롬프트를 웹에서 수정하는 기능을 만들지 않습니다. 워크플로 수정은 Studio에서만 합니다.

## 3. 타깃 사용자와 페르소나

| 페르소나 | 역할 | 상황 | 원하는 것 |
|---|---|---|---|
| 점검 담당자 A | 영업점·본부 실무자 (`INSPECTOR`) | 고객 서류를 다른 부서나 외부 기관에 보내기 전 | 문서를 올리고 위험 등급과 가려야 할 위치를 바로 확인 |
| 검토자 B | 개인정보보호 담당 (`REVIEWER`) | 자동 판정이 애매한 문서가 생겼을 때 | "사람 검토 필요" 문서만 모아 보고, 확인 결과를 기록 |
| 관리자 C | 서비스 운영 담당 (`ADMIN`) | 계정 발급과 감사 대응 | 계정과 역할 관리, 원문 열람 기록 조회 |
| 심사위원 | 대회 심사 | 시연을 볼 때 | 정확도, 판정 근거의 설명력, 보안 설계 확인 |

## 5. 사용자 스토리

- **US01 (F01):** 점검 담당자로서, 이메일로 가입하고 로그인해서 내 분석 기록을 따로 관리하고 싶다.
- **US02 (F02):** 점검 담당자로서, 문서를 올리고 지금 어느 단계까지 진행되었는지 보고 싶다. 1분 넘게 빈 화면을 보고 싶지 않다.
- **US03 (F03):** 점검 담당자로서, 결과 화면 맨 위에서 등급과 사람 검토 여부를 한눈에 보고 싶다.
- **US04 (F04, F05):** 점검 담당자로서, 문서의 어느 칸을 가려야 하는지 원본 위에서 바로 보고 싶다.
- **US05 (F06):** 점검 담당자로서, "본인 금융정보 결합 노출"이라는 판정이 문서의 어느 값 때문인지 눌러서 확인하고 싶다.
- **US06 (F08):** 검토자로서, 자동 판정이 확신하지 못한 문서만 모아서 보고, 확인 결과와 사유를 남기고 싶다.
- **US07 (F04, F09):** 관리자로서, 누가 언제 어떤 문서의 원문을 열람했는지 확인하고 싶다.
- **US08 (F12):** 심사위원으로서, 이 서비스가 평가 문서에서 얼마나 정확한지 근거를 보고 싶다.

## 6. 성공 지표

| 지표 | 목표 | 측정 방법 |
|---|---|---|
| 판정 정확도 | 평가 문서 10건 10/10 일치 | 웹에서 실행한 결과를 `eval/compare.py --plain`으로 채점 |
| 처리 시간 | 문서 1건 90초 이내 (2026-11-06 API 실측 36~67초) | 업로드부터 결과 표시까지 측정 |
| 위치 표시 정확도 | 발견 항목의 상자가 실제 값 위치와 일치 | 10건 화면을 눈으로 확인 |
| 시연 안정성 | 시연 중 오류 0건 | 리허설 3회 |
| 보안 | 로그에 원문값 0건, 권한 테스트 전부 통과 | 로그 검색, 역할별 접근 테스트 |

## 7. 제약 조건

- **판정 출처는 Studio 하나입니다.** Agent(환경 변수 `UPSTAGE_AGENT_ID`)와 Config ID(환경 변수 `UPSTAGE_CONFIG_ID`)를 고정해서 호출합니다. v4.2를 쓰려면 v4.2를 불러온 워크플로의 두 값으로 지정합니다. Config ID를 빼면 최신 설정이 실행되므로 반드시 지정합니다.
- 모든 Studio 요청에 `x-project-id` 헤더가 필요합니다. 빠지면 403 "No access to file" 오류가 납니다.
- Studio 작업은 비동기이며 문서 한 건에 36~67초가 걸렸습니다(2026-11-06). 웹훅은 없으므로 백엔드가 상태를 주기적으로 조회합니다.
- Studio 작업 하나에는 파일 하나만 넣을 수 있습니다.
- Studio에 올린 파일은 직접 지울 때까지 남으므로, 분석이 끝나면 백엔드가 지웁니다.
- 개발자는 사용자 한 명이며 프런트엔드와 백엔드를 모두 구현합니다.
- 로컬에서 먼저 만들고, 배포는 필요해지면 진행합니다.
- 요금은 팀의 Upstage Large 요금제로 충분하므로 비용 제약은 두지 않습니다.

업로드 파일의 크기와 쪽수는 서비스에서 제한하지 않습니다(2026-11-08 사용자 결정, 실제 문서는 20쪽을 넘는 경우가 많음). 다만 Studio 자체 한도(500MB, 1,000쪽)를 넘는 파일은 Studio 단계에서 실패합니다.

> ⚠️ 가정: v4.2는 평가 문서 10건과 서식 기반 합성 문서 40건(최대 51쪽)으로 시험했습니다. 합성 문서는 정답표가 없어 정확도를 확인하지 못했고, 긴 문서는 처리에 수 분이 걸립니다.
